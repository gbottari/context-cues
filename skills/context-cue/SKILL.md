# Context cue

A **context cue** is guidance that reaches the agent _when the work it governs begins_: not at session start, where it competes with everything else and fades before it is needed, and not on every edit, where it becomes noise. It is a hook with three parts: a cheap **trigger** on tool input, a per-session **marker** so it fires once, and the **cue text** emitted as `additionalContext`.

Installed cues live in `~/.claude/context-cues/`: each cue is a hook script `<name>.sh` beside its text `<name>.cue.md`, and a command cue also needs `command-position.sh` in that folder. With the Context Cues plugin, the shared helpers live in `${CLAUDE_PLUGIN_ROOT}/hooks/` and the plugin registers `rearm.sh` itself. If that path shows here unexpanded, the skill was installed by hand, and both helpers are already in `~/.claude/context-cues/`. This skill ships the two hook templates in `assets/`, the test helpers in `scripts/`, and the trigger traps in `references/`.

**Hook on the act, not on the skill.** A cue about a tool that a skill teaches could fire when the `Skill` tool loads that skill, but agents often run the tool without loading the skill (in the author's sessions, one CLI ran without its skill in 12 of 22 sessions), and a skill invoked as a slash command bypasses the `Skill` tool entirely. A cue about _doing_ something watches the doing. The same property lets a cue extend a third-party skill: the guidance lives in the cue, so the skill's own files stay untouched and its updates pull cleanly.

It is a hook, not a `.claude/rules` file: a path-scoped rule loads on the first read, write or edit of a matching file, whatever the work, and has no trigger for running a command or for a write through a Bash redirect ([trigger-design.md](references/trigger-design.md)); a file under `~/.claude/rules/` with no `paths:` loads on every session. Keep the cue text in a plain file outside that directory, beside the hook.

## Placement

Guidance reaches the agent one of three ways, and the axis is whether its relevance survives the distance from where it loads: `CLAUDE.md` is always present and fades as the session grows; a skill loads on a trigger, so it arrives already relevant; a hook fires at the tool call, where it neither fades nor can be reasoned away.

Keep a rule in `CLAUDE.md` when it holds for most of the work in the tree, or when the act that needs it leaves no clean signature to match. A high base rate pays for the always-on cost, and a weak trigger misfires. A rule about handling a repo's core data, in a repo where most work touches that data, stays in `CLAUDE.md` on both counts.

A context cue earns its place on the opposite profile: narrow scope, crisp trigger, and a real cost to the agent missing it.

## Steps

1. **Write the cue text** in `<name>.cue.md`. One short paragraph: the target behaviour, stated positively, and where fuller material lives. Done when the text reads as a standing rule, not as a complaint about one edit.
2. **Choose the triggers.** For a cue on writing files, two regexes: a _path_ gate (`\.tsx?([^[:alnum:]._-]|$)`, `(^|/)migrations/`) anchored to the end of a path token, and an _act_ trigger that names what the cue governs (`(^|[^:])//|/\*` for comment-writing, `CREATE TABLE` for schema work). Apply both to **what the call names and adds** (`file_path`, `edits[].file_path`, `new_string`, `content`, `command`), never to the raw payload (`tool_response` satisfies it for reads) and never to `old_string` (removing the thing would fire the cue). For `Bash`, require the path to be a _write_ target: a redirect, `tee`, or in-place `sed`/`perl`. For a cue on _running a command_, there is no path gate: gate the command's name at command position with `cue_command_re` from `command-position.sh`, so a command that only spells the name stays silent. Done when the act trigger names the act, not the file type. [trigger-design.md](references/trigger-design.md) has the five ways this goes wrong.
3. **Write the hook** in `~/.claude/context-cues/<name>.sh`. A file-write cue starts from [`file-cue-template.sh`](assets/file-cue-template.sh); a command cue starts from [`command-cue-template.sh`](assets/command-cue-template.sh), and sources `command-position.sh` from its own folder: with the plugin, copy `${CLAUDE_PLUGIN_ROOT}/hooks/command-position.sh` into `~/.claude/context-cues/` each time you build one, overwriting the old copy, so a plugin update reaches it. Order of operations is the whole cost story: grep the raw payload as a _reject-only_ prefilter (microseconds; a pattern absent from the whole payload cannot be in `tool_input`, but its presence proves nothing), then `test -e` the marker, and only then run `jq` for the authoritative gates and emit. The marker lives at `${XDG_RUNTIME_DIR:-${TMPDIR:-/tmp}}/context-cues/<session_id>/<cue-name>`. Use only bash, `jq`, and portable `grep -E` (no `\b`, no `\w`, no `-P`). Done when the hook is a shell script with no Python and no file scan.
4. **Register it** in `~/.claude/settings.json` under `PostToolUse` with the tool matcher and a short timeout, `rearm.sh` re-arms every cue on `compact` and `clear`, the two moments injected context is lost: the plugin registers it, and a manual install registers it once under `SessionStart` with the matcher `compact|clear`. PostToolUse is the event because PreToolUse cannot add context. Installing a hook is a config change the user approves; when the edit is denied, hand back the exact JSON entries and stop rather than retry or route around it. Confirm an edit that went through by reading the block back.
5. **Prove it fires once, with a matrix, not one payload.** Every misfire in [trigger-design.md](references/trigger-design.md) passes a single happy-path test. Write a test script that sources [`cue-test.sh`](scripts/cue-test.sh) and runs it with `bash`; its header shows the calls. A command cue gets `command_matrix` and `rearm_check`, which cover every way a shell runs the command, every mere mention, once per session, and re-arming. A file-write cue gets one `check` per trap in [trigger-design.md](references/trigger-design.md), each case its own `session_id`: the act through Edit, Write, MultiEdit and a Bash redirect (FIRED); deleting the text, editing beside text already there, only reading a matching file, a lookalike path (silent); the same `session_id` twice (FIRED, then silent); a `compact` payload through `rearm.sh` (FIRED again). Then the real check: in a fresh session, perform the act through Bash and confirm the cue appears as a system reminder (`claude --debug` logs hook output). Done when `finish` reports ok with a case for every trap and the reminder is observed in a live session, not reasoned about.

## Reference

- **Payload fields** (`code.claude.com/docs/en/hooks.md`): every event carries `session_id`; `SessionStart` carries `source` ∈ `startup|resume|clear|compact|fork`; `additionalContext` is honoured on `PostToolUse`, `UserPromptSubmit`, `SessionStart`, `SubagentStart`, `Stop`, not `PreToolUse`.
- **Matchers** filter on tool _name_ only (exact or unanchored regex). Any predicate on tool _arguments_ has to live in the script, hence grep first.
- **Subagents** share the parent's `session_id` but not its context. A cue fired in the parent never reaches a subagent, and the marker keeps it from firing there; `SubagentStart` is the event to deliver it to subagents if that matters.
- **Output cap** is 10,000 characters per hook; longer text is spilled to a file and replaced by a 2 KB preview. A cue that needs more keeps its text in a doc and injects a pointer to read it.
- **Windows.** Hooks run in Git Bash when Git for Windows is installed, and cannot run these scripts without it. Commands the agent runs through the PowerShell tool reach hooks as `tool_name: "PowerShell"`; match `Bash|PowerShell` for a command cue that should see them, knowing `cue_command_re` assumes bash syntax.
